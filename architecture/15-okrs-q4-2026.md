## 1. OKRs

### O1. Sustainable long-term contract engagements (north star, unchanged)

| KR | Q4 target | Source |
|---|---|---|
| KR1 New engagements signed | 3 *(proposed)* | `outcomes` where `outcome_type = 'engagement_signed'` |

## 2. Qualification

Use the existing scoring, not a new definition. A lead is qualified when:

- **Inbound:** Roy Kent marks it high-fit (`prospects.icp_fit_score`, `36-inbound-leads.md`).
- **Cold:** it enters a sequence, which already requires stage, function state, and S1–S5 scores (`outreach_targets_seq_ck`).

## 3. Gaps

### Mismatches — data exists but does not match the KR

| ID | Gap | Effect | Fix |
|---|---|---|---|
| M1 | `outcomes.attributed_prospect_id` references `prospects` (inbound) only. There is no link to `outreach_targets`. | Revenue from cold outreach cannot be attributed to a target, trigger, or hypothesis. | Add `attributed_target_id BIGINT REFERENCES outreach_targets(id)`. **Schema written 2026-10-05:** migration 0030, `PRD-outcome-attribution.md`. |
| M2 | Calls and engagements are recorded twice: `outreach_targets.status` (`call_booked`, `engaged`) and `outcomes` (`discovery_call_booked`, `engagement_signed`), both by hand. | The two counts will diverge, and KR2.5 double-counts if both are summed. | Count outreach calls from status transitions; use `/outcome` only for non-outreach calls. Or have a status change to `call_booked`/`engaged` prompt the `/outcome` entry with the target pre-linked (needs M1). |
| M3 | `v_outreach_hypothesis_results` and the W8 dashboard counts read *current* status. A target that moves `call_booked` → `engaged` drops out of `calls_booked`. | Quarterly funnel counts undercount as deals progress. | Compute Q4 counts from `outreach_events` status transitions, not current status. |
| M4 | `outcomes.outcome_value` has no defined meaning: monthly fee, total contract, or first invoice. | KR2 is not comparable across deals. Retainers and projects can't be summed. | **Resolved 2026-10-05:** `outcome_value` is total contract value; a maintenance agreement records its first term. Enforced by the `/outcome` label (`PRD-outcome-attribution.md` D4). |
| M5 | `outcomes` has no client key. `engagement_signed` and a later `maintenance_converted` for the same client are linked only by free-text description. | KR3 cannot be computed. | Add a client key. **Schema written 2026-10-05:** `clients` table + `outcomes.client_id`, migration 0030, `PRD-outcome-attribution.md`. |
| M6 | ~~KR3 is meaningless if engagements are sold as retainers.~~ | — | **Resolved 2026-10-05:** engagements are sold as projects first. KR3 stays as project → maintenance conversion. |
| M7 | Outreach conversion rates are gated at 40 completed sequences. | O2 targets must be counts in Q4, not rates. | Done in §1. Revisit in Q1 2027. |
| M8 | Deterministic outreach loops write no `agent_runs` rows (`loops/README.md:81`). | KR4.2 ignores the loops that feed O2. | Add a non-billable run row per loop, or derive loop health from Ted's heartbeats. |
| M9 | `GLOBAL_DAILY_CEILING` is $25/day (`agents/_lib/runs.py:117`), about $750/month. No monthly budget exists. | KR4.3 has a guard rail but no target. | Operator sets a monthly budget. |

### Important data the dashboard does not show

The Higgins format in `80-telemetry-layer.md` does not include:

| Data | Table | Why it matters |
|---|---|---|
| Overdue client follow-ups | `follow_ups` (`deadline`, `status`) | Missed commitments to clients and prospects hurt KR1 and KR3 directly. W4 reports only how many were extracted. |
| Relationships past cadence | `people.last_contacted_at`, `cadence_days` | Existing clients going quiet is the earliest KR3 warning. |
| Hypothesis results | `v_outreach_hypothesis_results` | Shows which segments produce replies and calls. This decides where the next sequences go. |
| Autonomous sourcing yield | `outreach_sourcing_runs`, `outreach_discoveries` | Shows whether sourcing keeps the 15 slots filled (KR2.1) and the accept/reject rate. |
| Items waiting on the operator | `approval_queue`, `outreach_discoveries` awaiting review | The pipeline stalls on the human gate, not the agents. |
| Overdue tasks | `tasks.due_date`, `status` | Same reason. |

### Build prerequisite

Higgins is not built. No code under `agents/` implements it, and the `dashboard` table is a single-row heartbeat. Every dashboard in this file depends on building Higgins first.
